Four shapes the frontend could take

The current spec describes a correct, conventional admin app. These four directions ask what the product looks like when UX smoothness is the first principle, ranging from a disciplined evolution of the current design to a different application architecture entirely. Full write-ups live in proposals/ on the branch; this page is the visual tour.

The panel is a route, not a modal: refresh restores it, the back button closes it, and the link can be pasted to a teammate. Modals survive only as confirmations.

What it adds

  • Panel router - every edit surface is a query-param route
  • Cmd+K palette - navigate, create, act; instant via cache
  • Entity chips - hover previews, no dead-end strings
  • Query cache - stale-while-revalidate + optimistic writes
  • Motion spec - 3 durations, 2 easings, all tokens

What it drops

  • The modal edit stack (EditSurfaceHost)
  • Fetch-on-mount store methods
  • Spinners after first paint

Choose when

  • You want maximum UX gain per week
  • Nothing here is throwaway - A is the foundation B stands on

What it adds

  • Dock manager - resizable, collapsible, state per agent

What it replaces

Choose when

  • Composition is the product's identity
  • The daily user builds agents, and the demo matters - this is the direction people show other people

What it adds

Choose when

  • "Why did that run go wrong" is the daily question
  • Pairs with B later: B builds, C observes
D

Tiled Workspace

A different architecture, not a restyle. No fixed views: every surface is a pane type, the layout is a user-composed split tree serialized into the URL, and panes link through selection channels like a trading terminal. Ships with preset workspaces so day one still looks like an app.

One click on the canvas node retargeted the editor pane and highlighted the tool's frames in the thread pane: three specs, one shared selection, zero navigation. The layout string in the URL is the whole app state.

What it adds

  • Pane manager - split tree, tab stacks, drag to dock
  • Link channels - shared selection across panes
  • Entity cache - normalized, WS-fed; panes cannot disagree
  • Command registry - palette, menus, keys: one source

What it risks

  • Blank-slate paralysis - presets are load-bearing
  • Longest path to first usable screen
  • Desktop-only by nature

Even if not chosen

  • Its data layer (cache, bus, commands) is worth adopting under A or B
  • B's docks are a fixed pane layout: Studio can grow into D without a rewrite
Recommendation

Ship A as the foundation, evolve toward B, and adopt C's trace timeline regardless.

A replaces the current spec's weakest parts (modal editing, fetch-on-mount stores, no keyboard layer) while keeping every view spec valid, and it deliberately builds the three pieces B needs anyway: the palette, the panel router, and the query cache. When the canvas matures, promoting it from a view to the workspace is a shell-level change, which the swappability mandate exists to make cheap. C's timeline is the highest-value inspector upgrade and works in any direction. D's data layer is the reference architecture for the cache and event bus even if tiling never ships.
